# هدية — Lean MVP (بريدة)

**DISCOVERY + DISCOUNT + DIRECT ORDER**

منصة تربط العميل بمطاعم وكافيهات محلية في بريدة عبر "هدية يومية" مفاجئة، ثم تحوّل الاكتشاف
إلى طلب مباشر من المطعم. المنصة **لا تقوم بالتوصيل** ولا **لا تمر أموال العميل بحسابها**.

> **BUILD LESS · MEASURE MORE · LEARN FAST**

## 1) السؤالان اللذان نختبرهما

1. **هل فتح هدية تحتوي على خصم من مطعم محلي يؤدي فعلاً إلى طلب مؤكد؟**
   → المؤشر: `Completed Orders Generated Per Gift` (North Star).

2. **هل المطعم يرى أن دفع رسوم ثابتة على الطلب الناجح أقل تكلفة وأكثر فائدة له؟**
   → المؤشر: هل المطاعم تدفع رسوم كشف الحساب فعلاً أم لا؟

إذا كانت الإجابة (2) لا، يجب تغيير نموذج الإيرادات **قبل** بناء أي ميزة جديدة.



> يعطيك `0 rows`؟ يعني البريد غير مطابق — تأكد أن الحساب **مُؤكَّد** (Confirmation)
> وأن البريد مكتوب كما هو تماماً.

### ب) التشغيل محلياً
```bash
npx serve .          # أو أي سيرفر ملفات ثابت
```
ثم افتح `http://localhost:3000`.

> **لا تفتح الملفات بـ `file://`** — المتصفح يمنع ES Modules وطلبات الشبكة.
> لكن **RLS على anon مفصول بـrevoke**، لذا `http://localhost` آمن للتطوير.

### ج) ربط الواجهة
في النشر على GitHub Pages يجب إضافة القيمتين في إعدادات المستودع أو بيئة
`github-pages` تحت **Settings → Secrets and variables → Actions**:
- `SUPABASE_URL`: رابط مشروعك مثل `https://xxxx.supabase.co`
- `SUPABASE_ANON_KEY`: المفتاح العام (anon/publishable key) من Project Settings → API

ينشئ workflow ملف `assets/js/runtime-config-live.js` أثناء النشر. لا تضع `service_role`
key في المستودع أو في الواجهة. الإدخال المحلي محفوظ في المتصفح للتطوير فقط، ولا
يُطلب من العملاء على الموقع المنشور.

بعد تشغيل SQL migrations، تأكد من تطبيق `0005_site_visitors.sql` حتى يعمل عداد
الزوار في الصفحة الرئيسية؛ هذا الملف ينشئ دالة `site_visitor_count()` ويمنحها
صلاحية التنفيذ للزوار.

وبعده `0007_whatsapp.sql` — يضيف `restaurants.whatsapp` و`whatsapp_orders_enabled`
وكوداً قصيراً لكل هدية (`daily_gifts.code`) ودوال مشاركة الفاتورة
(`customer_order_share` · `staff_order_share`). أرقام الواتساب تُطبَّع على السيرفر
إلى صيغة `9665xxxxxxxx`، وأي رقم بغير هذه الصيغة يُرفض برمز `invalid_whatsapp`.

ثم `0008_delivery.sql` — يضيف رسوم التوصيل لكل منشأة (انظر §4) وشرط تأكيد العميل
للسعر.

ثم `0009_consents.sql` — موافقة مُقيَّدة بغرضها (نص الغرض + نسخة السياسة + وقتها +
مصدرها)، ومشاركة الجوال **اختيارية للاستلام ومطلوبة للتوصيل فقط**، وإخفاء الرقم عن
المنشأة (مقنّعاً) ما لم يوافق العميل، وبوابة تسويق لا تُعرض بدونها أي رسالة.

ثم `0010_loyalty.sql` — نقاط تصدرها المنشأة بعد مسح باركود الطلب، وتُعتمد في رصيد
العميل عند اكتمال الطلب فقط (استحقاق وعرض — بلا استبدال ولا رصيد مالي).

لا يُشترط تطبيق الهجرات بالترتيب الرقمي فقط، بل **كل هجرة على حدة** ومع كل
واحدة يُشغَّل `npm run check` للتأكد أن الثوابت والرموز ما زالت متوازنة.

### د) النشر (اختياري — مجاني)

### هـ) الفحص التلقائي

npm run smoke     # سيرفر محلي مؤقت + التأكد أن كل مرجع داخلي موجود

خمس طبقات فحص — شغّلها **قبل** رفع أي ملف SQL إلى Supabase:

| الأمر | ماذا يفحص |
|---|---|
| `check:sql` | بنية SQL: توازن الأقواس، اكتمال كل جدول، انتهاء كل ملف بفاصلة منقوطة |
| `check:pg` | تحليل كل هجرة بمُحلِّل PostgreSQL الحقيقي (`libpg-query`) |
| `check:invariants` | **176 ثابت عمل**: منع تكرار الهدية، نطاق الخصم، حصر الرسوم عند `COMPLETED` فقط، رسوم التوصيل من صف المنشأة (لا من المتصفح)، تأكيد العميل للسعر قبل القبول، الجوال شرط للتوصيل فقط، سجل الموافقات إضافي فقط، النقاط تُعتمد عند الاكتمال ولا تدخل أي حساب مالي، RLS، وأن الواتساب قناةُ توصيلٍ لا تتجاوز النظام… |
| `check:errors` | أن كل رمز خطأ تُعيده قاعدة البيانات (من كل الهجرات) له معالجة في الواجهة |
| `check:modules` | بنية كل وحدة JS مضمّنة في HTML + `assets/js/*.js` (منها `barcode.js`) |

## 4) دورة الطلب والرسوم

```
NEW → ACCEPTED → PREPARING → READY → COMPLETED
 └────────────→ CANCELLED / NO_SHOW
```

- **الرسوم تُنشأ عند `COMPLETED` فقط** — داخل `transition_order()`.
- `platform_fee` تُلتقط كنسخة على الطلب وقت الإكمال (لا تتغير كشوف الماضي).
- `restaurant_ledger` له قيد `unique(order_id, entry_type)` → **لا يمكن توليد رسوم مرتين**.
- الطلبات الملغاة أو غير المكتملة = **صفر رسوم**.

### قناة واتساب (`0007_whatsapp.sql`)

واتساب **قناة توصيل للفاتورة**، وليس نوع طلب ولا مساراً يتجاوز النظام:

1. الطلب يُنشأ أولاً عبر `create_order` — الخصم والإجمالي وكود الهدية تُحسب على السيرفر.
2. بعد نجاح الإنشاء يظهر في `checkout.html` اختيار: **أرسل الفاتورة عبر واتساب**
   أو **متابعة داخل المنصة** (حتى لو ضغط خارج النافذة ينتقل لمتابعة الطلب).
3. زر واتساب يستدعي `customer_order_share` فيُعيد نص الفاتورة جاهزاً (الأصناف + الإجمالي +
   الخصم + كود الهدية + طريقة الاستلام) مع رقم واتساب المنشأة المطبَّع.
   المتصفح يبني رابط `wa.me` فقط ولا يحسب أي رقم.
4. أول إرسال يُسجَّل في `orders.whatsapp_shared_at` — بلا رسوم وبلا حالة طلب جديدة.
5. المنشأة تتحقق من كود الهدية في `/r/orders.html` (يظهر `daily_gifts.code` بجانب الطلب)،
   ويمكنها إرسال الفاتورة للعميل عبر `staff_order_share`. الإدارة ترى في
   `/admin/restaurants.html` من فعّل القناة.
6. بلا رقم واتساب أو بإيقاف `whatsapp_orders_enabled` يبقى المسار داخل المنصة كما هو.

### التوصيل ورسومه (`0008_delivery.sql`)

- **الرسوم لكل منشأة**: `restaurants.delivery_fee` يحددها صاحب المنشأة من `/r/profile.html`،
  والأدمن يضع سقفاً عاماً (`delivery_fee_max` في `/admin/settings.html`).
- **السيرفر هو المرجع**: `create_order` لا يستقبل أي مبلغ من المتصفح — يقرأ الرسوم من صف
  المنشأة عبر `delivery_fee_for()` (دالة داخلية غير منشورة في الـ API)، وtrigger
  `trg_restaurants_delivery_fee` يقيّد أي كتابة (حتى المباشرة) بالسقف وبلا سالب.
- `order_total = subtotal − discount + delivery_fee` — والعميل يرى الرسوم في
  `gift.html` و`menu.html` و`checkout.html` قبل إنشاء الطلب.
- **تأكيد السعر إلزامي عند وجود رسوم توصيل**: الطلب يُنشأ بحالة `new` و`price_confirmed_at = null`،
  ولا يستطيع الموظف قبوله (`accepted`) قبل أن يؤكد العميل المبلغ نفسه عبر
  `customer_confirm_order_price` (يرسل الرقم الذي رآه؛ أي اختلاف = `price_changed`).
  الطلب بلا رسوم توصيل يُؤكَّد تلقائياً عند الإنشاء لأنه لا يحمل عنصر سعر جديداً.
- **تغيير طريقة الاستلام** قبل بدء التنفيذ عبر `set_order_delivery` (للعميل وجهازه فقط):
  يُعاد حساب الرسوم ويُلغى التأكيد السابق، وبعد مغادرة حالة `new` يُرفض بـ`invalid_delivery_change`.
- **لا رسوم منصة على التوصيل**: أساس الرسوم `order_total − delivery_fee`، والمنشأة تحصّل
  رسوم التوصيل كاملة — لذلك `restaurant_net = order_total − platform_fee`.
- **إصلاح**: كانت `restaurant_net` في `0003` تخصم الخصم مرّتين (`order_total − discount − fee`)
  بعد أن كان `order_total` يتضمن الخصم أصلاً. الصيغة الصحيحة مثبتة الآن بثابت في `check:invariants`.
- `orders.price_confirmed_total` يحفظ المبلغ المؤكَّد، و`restaurant_ledger.delivery_fee`
  يفصل رسوم التوصيل في كشف المنشأة (ولا تدخل في «المستحق» للمنصة).

### الموافقة المقيَّدة بالغرض (`0009_consents.sql`)

- **الجوال ليس ثمناً لاستخدام المنصة**: مشاركته **اختيارية للاستلام** و**شرط للتوصيل فقط**
  (المندوب يحتاجه). من يستلم بنفسه لا يُطلب منه رقم ولا موافقة —
  `orders.customer_phone` صار يقبل `null`، والقيد `orders_delivery_phone_required`
  يمنع توصيلاً بلا رقم صحيح.
- **الرفض يُسجَّل صراحةً**: كل طلب يُنشئ صف موافقة — `granted` عند المشاركة و`revoked`
  عند الرفض، مع **نص الغرض كما رآه العميل**، ونسخة السياسة، والوقت، والمصدر، ورقم الطلب.
  لا نستنتج «عدم الموافقة» من غياب السجل.
- **السحب لا يمحو السجل**: `set_consent`/`set_order_phone` تضيفان صفاً جديداً،
  والحالة الفعّالة = أحدث صف لنفس (الجهاز، المنشأة، الغرض) عبر `consent_active()`.
  ولا يوجد أي `set consent_status` ولا `delete from consents` في الهجرة (ثابت مفروض).
- **الإخفاء حقيقي لا تجميلي**: `restaurant_orders` و`staff_order_by_code` تعيدان
  `05••••1234` و`phone_shared:false`، و`staff_order_share` تُرفض بـ`phone_not_shared`،
  والفاتورة لا تطبع الرقم بلا مشاركة، و`revoke select on public.orders from anon, authenticated`
  يجعل التسريب من المتصفح مستحيلاً حتى لو تغيّرت RLS لاحقاً (القراءة عبر دوال
  `security definer` فقط).
- **بوابة التسويق**: موافقة التسويق ليست شرطاً لأي طلب. `customer_ad` لا تُعيد أي محتوى
  تسويقي بلا موافقة فعّالة (`no_marketing_consent`)، و`restaurant_marketing_audience`
  تُعيد **العدد فقط** — لا أرقام ولا معرّفات أجهزة.
- نص الغرض محفوظ في `app_settings` (`consent_purpose_order_contact` · `consent_purpose_marketing`)
  وقابل للتعديل بلا كود، **لكن** نص كل موافقة قديمة يبقى كما رآه العميل لحظة الموافقة.
- سجل الموافقات الكامل مرئي للعميل في `/account.html` مع زر سحب/موافقة لكل غرض.

### النقاط وباركود الطلب (`0010_loyalty.sql`)

- **استحقاق وعرض فقط**: لا استبدال، ولا خصم، ولا رصيد مالي، ولا محفظة. `customer_points`
  تُعيد `redeemable: false`، ولا توجد أي دالة استبدال.
- **الرصيد = مجموع الصفوف المعتمدة** (`status = 'applied'`). لا عدّاد مخزَّن، فلا يمكن
  أن يختلف الرصيد عن السجل.
- **الدفتر إضافي فقط** (`points_ledger`): لا حذف، ولا تعديل على المبلغ أو الطرفين.
  التعديل الوحيد المسموح يفرضه trigger `trg_points_ledger_guard`: `pending → applied|cancelled`.
- **صف واحد لكل طلب** (`unique(order_id)`) — لا تكرار للنقاط على الطلب نفسه
  (`points_already_granted`، مع التقاط سباق `unique_violation`).
- **التدفق**: المنشأة تحدد `points_enabled` و`points_per_order` و`points_max_per_order`
  من `/r/profile.html` داخل سقف الإدارة `points_hard_cap`؛ الموظف يمسح كود الطلب في
  `/r/scan.html` ثم يمنح النقاط (صف `pending`) ثم يؤكد التسليم — و`transition_order`
  يحوّلها إلى `applied` **داخل فرع `COMPLETED` وحده**. الطلب الملغي/لم يحضر يحوّل
  الصف المعلَّق إلى `cancelled` فلا يُعتمد أبداً.
- **لا أثر مالي**: النقاط لا تدخل `restaurant_ledger` ولا `monthly_statements` ولا
  أساس `platform_fee`. تظهر في اللوحة وكشف الحساب كرقم معلوماتي فقط.
- **الباركود = كود الطلب نفسه**: 6 خانات hex داخل مجموعة Code 39، فلا نحتاج كوداً ثانياً
  ولا مكتبة خارجية — `assets/js/barcode.js` يبني SVG متجهياً محلياً بلا CDN
  (رسم Code 39 قياسي بنسبة 3:1 ومنطقة هادئة على الجانبين). العميل يعرضه في `/order.html`
  والموظف يقرأه في `/r/scan.html` عبر `staff_order_by_code` (مقصور على منشأة الموظف،
  ويرفض أي كود بغير الصيغة بـ`invalid_order_code`).
- **الحد الأعلى = 100 نقطة افتراضياً** (`points_hard_cap`)، وحارس
  `trg_restaurants_points` يفرضه على أي مسار كتابة حتى المباشرة.

## 5) منطق الخصم

المطعم يحدد `[min_discount, max_discount]` فقط. النظام يختار قيمة **داخل النطاق**
- مضمونة ≥ الحد الأدنى (لا يُعرض خصم أقل مما سمح به المطعم)
- ثابتة لنفس (جهاز + عرض + يوم) → نفس النتيجة عند إعادة الفتح
- بلا أرقام مخترعة ولا قواعد إضافية

الإعدادات في `/admin/settings.html`: `platform_fee`, `gifts_per_day`,
`min_discount_floor`, `discount_step`, `discount_strategy`, حدود الحملات.

## 6) الافتراضات والقيود

### ASSUMPTION
- **رسوم المنصة = 0 افتراضياً.** المتطلبات لم تحدد قيمة، والنظام لا يفترض رقماً.
  تُضبط من `/admin/settings.html` ثم تُختبر أكثر من قيمة.
- **أسماء الأحياء في الـseed بيانات تشغيلية** وليست قائمة أحياء بريدة الرسمية —
  استبدلها قبل الإطلاق الحقيقي.
- عداد الزوار في الصفحة الرئيسية يعرض عدد الأجهزة الفريدة المسجلة فعلياً، ولا يعرض رقماً
  افتراضياً عند غياب إعداد قاعدة البيانات.
- **واتساب المنشأة اختياري**، ويُخزَّن بصيغة `9665xxxxxxxx`. المفتاح الدولي `966` وبداية
  الرقم بـ `5` **ثابتان في هذه النسخة** لأن المنصة في بريدة؛ أي صيغة أخرى تُرفض.
  القناة لا تنشئ طلباً ولا تحسب خصماً ولا تضيف رسوماً: `order_type` يبقى `pickup`/`delivery`.
- **سقف رسوم التوصيل = 25 ر.س افتراضياً** (`delivery_fee_max`). المتطلبات لم تحدد أي قيمة،
  فالقيمة قابلة للتغيير من `/admin/settings.html`، وحذف الإعداد يصفّر السقف (لا رسوم توصيل).
  المنشآت التي كان توصيلها مفعّلاً قبل `0008` تبدأ برسوم **صفر** حتى تحدد رسومها بنفسها —
  لا قيمة مخترعة نيابة عنها.
- **تأكيد السعر** مطلوب فقط عندما يضيف الطلب عنصر سعر جديداً (رسوم توصيل). هذا هو التفسير
  الافتراضي لـ«تأكيد العميل للسعر» ويمكن تشديده ليغطي كل الطلبات إن تغيّر القرار.
- **سقف النقاط = 100 نقطة افتراضياً** (`points_hard_cap`). المتطلبات لم تحدد قيمة،
  فالقيمة قابلة للتغيير من `/admin/settings.html`، وحذف الإعداد يصفّره (لا نقاط تُمنح).
  المنشآت تبدأ بـ`points_enabled = false` — لا نقاط مفروضة على أحد.
- **النقاط استحقاق وعرض فقط في هذه المرحلة** — لا استبدال ولا خصم ولا محفظة ولا رصيد مالي،
  ولا انتهاء صلاحية. أي استبدال لاحق قرار منفصل يحتاج نموذجاً محاسبياً واضحاً.
- **نصوص أغراض الموافقة صياغات تشغيلية** محفوظة في `app_settings` — ليست نصاً نظامياً
  معتمداً، وتحتاج مراجعة الجهة المختصة (انظر أدناه). ولأن النص يُحفظ داخل كل موافقة،
  تحديث الصياغة لاحقاً لا يغيّر دلالة موافقة قديمة.
- **الباركود Code 39 يُقرأ يدوياً في هذه المرحلة**: صفحة المسح تستقبل الكود المكتوب،
  ولا تستخدم كاميرا الجهاز. إضافة قراءة الكاميرا مرحلة منفصلة.
- **تعبئة السجلات القديمة تعمل مرة واحدة** (`consents_backfill_at` · `delivery_backfill_at`):
  الطلبات السابقة على `0009` تُعتبر «الرقم مشارَك» لأن الموافقة كانت إلزامية حينها،
  وإعادة تشغيل الهجرة لا تُغيّر قراراً سابقاً.

### REQUIRES OFFICIAL VERIFICATION
- **التوصيل بالدراجات داخل الأحياء** — لا يفترض النظام أنه مسموح. «توصيل المطعم»
  يعني أن المطعم هو المنفّذ. أي تشغيل للدراجات مرحلة منفصلة تعتمد على متطلبات
  هيئة النقل والجهات المختصة.
- **حماية البيانات ومشاركة رقم الجوال** — الموافقتان منفصلتان والمسجَّل،
  لكن المتطلبات النظامية تحتاج مراجعة الجهة المختصة.
- **نصوص أغراض الموافقة** (`consent_purpose_order_contact` · `consent_purpose_marketing`)
  صياغات تشغيلية داخل `app_settings` — **ليست نصاً نظامياً معتمداً**، وتحتاج اعتماد
  الجهة المختصة قبل الإطلاق. نفس الأمر على `policy_version`.
- **النقاط** برنامج ولاء تصدره كل منشأة لنفسها. لا استبدال ولا قيمة نقدية في هذه المرحلة،
  لكن أي تحويل لاحق إلى مزايا يحتاج مراجعة نظامية ومحاسبية.
- **الفوترة / الضريبة** — غير منفَّذة. التصميم يحتمل إضافتها لاحقاً.
- **رسوم التوصيل** مبلغ تحدده المنشأة ويُحصَّل لها مباشرة (لا تمر أموال العميل بحساب المنصة)،
  لكن أي متطلب نظامي حول رسوم التوصيل أو إظهارها للعميل يحتاج مراجعة الجهة المختصة.
